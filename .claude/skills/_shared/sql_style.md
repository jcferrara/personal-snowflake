# SQL Style (shared reference)

SQL formatting and query-structure conventions. Source: dbt Labs "How we style our SQL."

## Basics

- **Lint with SQLFluff.** Customize `.sqlfluff` to your needs; exclude paths via
  `.sqlfluffignore` (exclude `target/`, `dbt_packages/`, `macros/`). The `sqlfmt`
  formatter is also available.
- **Lowercase** all keywords, field names, and function names.
- **Indentation: four spaces.**
- **Line length:** ~80 characters is a guideline, but **readability wins** — never
  break an expression awkwardly just to stay under the limit (see Readability below).
- **Use trailing commas.**
- **Alias explicitly with `as`** when aliasing a field or table.
- **No keyword column alignment**: never pad with extra spaces to line
  up `as`, `>`, `=`, or other keywords across rows. Use a single space. Padding
  fights every future edit (one rename and the whole column needs re-aligning)
  and adds noise to diffs. Example — do this:
  ```sql
  count(*) as baseline_sample_count,
  avg(metric_value) as baseline_mean,
  stddev(metric_value) as baseline_stdev
  ```
  not this:
  ```sql
  count(*)             as baseline_sample_count,
  avg(metric_value)    as baseline_mean,
  stddev(metric_value) as baseline_stdev
  ```

> **Project override — comments.** **Never use Jinja comments (`{# #}`) in model SQL.**
> Only two comment styles are allowed:
> 1. **CTE header — `/* ... */`.** **Every functional CTE gets a `/* */` header of 1–3
>    plain-English sentences** placed immediately before it, describing what the following
>    CTE does so a reader understands it at a glance. This is required, not just for
>    non-obvious CTEs. (Import CTEs — including those generated by `import_models` — are
>    self-describing and don't need individual headers.)
> 2. **Inline — `-- ...`** on its own line or end-of-line, to describe a specific piece of
>    **business logic** being applied (a non-obvious filter, a magic constant, a
>    workaround) so a reader understands *why* the logic exists.
>
> Don't use `/* */` mid-CTE (header position only); anything 2+ sentences belongs in a
> `/* */` header rather than stacked `--` lines.
>
> **Keep comments concise.** Don't restate what the SQL already says or over-explain
> obvious logic — a comment earns its place only by adding context the code can't (the
> *why*, a magic constant, a caveat). Prefer one tight sentence over several.

## Readability first

> **Always optimize SQL for human readability** — not for fewer lines of code, and not
> for fewer characters on a line. If a choice trades clarity for brevity, choose clarity.

A concrete consequence: **keep a join condition on one line** (`on left.key = right.key`).
Don't split an `=` across lines to satisfy a character limit.

```sql
-- ✅ readable: each condition reads as one thought
from transaction

left join account
    on transaction.account_id = account.account_id

left join category_map
    on transaction.category_id::text = category_map.source_id
    and category_map.source_name = 'finance'

-- ❌ harder to read: the = is broken onto its own line
from transaction

left join account
    on transaction.account_id
    = account.account_id

left join category_map
    on transaction.category_id::text
    = category_map.source_id
    and category_map.source_name
    = 'finance'
```

## CTEs over subqueries

Always prefer CTEs to subqueries. There are two kinds:

### Import CTEs

- Place **all `{{ ref('...') }}` / `{{ source(...) }}` statements in CTEs at the top
  of the file.**
- **Name an import CTE after the table it references.**
- **Limit data scanned** — select only the columns you use and add `where` clauses to
  filter unneeded rows where possible.

> **Project override — `import_models` macro.** In intermediate, mart, exports, and
> metrics layers, use the `import_models(refs=[...], ctes=[...])` macro
> (`macros/import_models.sql`) for every `ref()` instead of hand-writing import CTEs —
> it expands to one import CTE per `ref()`, keeping the top of every file uniform.
> `refs` and `ctes` must be the same length; CTE names use business meaning
> (`garmin_activities`, not `stg_garmin__activities`). Hand-written import CTEs
> remain correct in two cases: staging models reading from `source()`, and the
> incremental source of an `incremental` model (see incremental note below).

```sql
with transactions as (
    select
        transaction_id,
        account_id,
        amount_usd,
        transaction_date
    from {{ ref('transactions') }}
    where transaction_date >= '2020-01-01'
)
```

### Functional CTEs

- Each CTE should perform a **single, logical unit of work** (where performance
  permits).
- **Name CTEs as verbosely as needed** to convey what they do —
  `events_joined_to_users`, not `user_events`.
- **Refactor duplicated CTEs across models into their own intermediate models.** Watch
  for repeated chunks of logic.
- **The last line of a model is `select * from <final_cte>`.** This makes it easy to
  materialize and audit any step — just change the CTE in the final select to inspect
  its output during development.

```sql
with events as (
    ...
),
/* CTE header comments go here (this repo uses /* */ + --, never {# #}) */
filtered_events as (
    ...
)

select * from filtered_events
```

### No subqueries

> **Project override.** **Never use subqueries.** Every `select` belongs in its own
> top-level CTE — not nested inside another `select`, `from`, `join`, `where`, or a
> select-list expression, regardless of size. If you need an intermediate result, name
> it as a CTE and reference it. This includes scalar subqueries in `where`
> (`where x > (select max(...) from ...)`) and derived tables in `from`
> (`from (select ...) as t`) — promote both to CTEs. For the incremental `max()`
> cutoff, use a dedicated `cutoff` CTE (see the incremental note below).

## Fields, aggregations, grouping

- **State fields before aggregates and window functions.**
- **Aggregate as early as possible** (on the smallest dataset) before joining, to
  improve performance.
- **Group/order by column numbers** (`group by 1, 2`) is preferred over listing names.
  If you're grouping by more than a few columns, reconsider the model design.

## Joins

- **Prefer `union all` to `union`** unless you explicitly want to dedupe.
- **When joining 2+ tables, always prefix column names with the table name.** If
  selecting from only one table, prefixes aren't needed.
- **Be explicit about join type** — write `inner join`, not `join`.
- **No letter / non-descriptive table aliases**: single-letter aliases like
  `c.` or `o.` aren't descriptive — a reader has to scroll up to remember which table
  `c` refers to. Prefix columns with the full table name (preferred), or use a
  meaningful descriptive alias if the full name is genuinely too long.
- **Always move left to right.** A `right join` usually signals you should swap which
  table is in `from` and which is `join`ed.

## Model configuration in SQL

- Put **model-specific attributes** (e.g. sort/dist keys) in the model's config block.
- Put **configuration that applies to all models in a directory** in `dbt_project.yml`.
- In-model config block for readability:

```sql
{{
    config(
      materialized = 'table',
      sort = 'id',
      dist = 'id'
    )
}}
```

## Testing convention

> **Project override — keep tests minimal.** The **only** tests an AI agent should add
> are **`unique` + `not_null` on the table's primary key**:
> - **Use the source id as the primary key when one exists** (e.g. `user_id` on
>   `dim_users`).
> - **If the model is at a new grain that doesn't exist in the source, build a dbt
>   surrogate key** with `dbt_utils.generate_surrogate_key([...])` (named `sk` /
>   `<entity>_sk`) and test `unique` + `not_null` on that.
>
> **Do not add any other tests unless explicitly asked** — no `accepted_values`,
> `relationships`, side-column `not_null`, or range checks. A test should be something we
> can act on; randomly adding tests just creates noise. For a composite grain, collapse
> it into one surrogate key (preferred) or use `dbt_utils.unique_combination_of_columns`
> (the built-in `unique` test silently ignores a `column_name:` override). Use
> `severity: warn` only when explicitly asked and the source legitimately allows the
> condition.

## Incremental cutoff CTE

Because subqueries are banned, replace the standard dbt scalar-subquery cutoff
(`where updated_at > (select max(updated_at) from {{ this }})`) with a `cutoff` CTE, and
keep imports via `import_models` with the incremental source hand-written just after:

```sql
with

{{
    import_models(
        refs = [ref('stg_finance__accounts'), ref('stg_finance__categories')],
        ctes = ['accounts', 'categories']
    )
}},

{% if is_incremental() %}
cutoff as (

    select dateadd('day', -30, max(updated_at)) as cutoff_at
    from {{ this }}

),
{% endif %}

recent_transaction as (

    select recent_transaction.*
    from {{ ref('stg_finance__transactions') }} as recent_transaction
    {% if is_incremental() %}
    inner join cutoff
        on recent_transaction.updated_at >= cutoff.cutoff_at
    {% else %}
    {{ dev_environment_filter('updated_at') }}
    {% endif %}

),

-- functional CTEs follow
```

The `dbt_utils.generate_surrogate_key` cutoff lookback (`dateadd('day', -30, ...)`) is
the lookback window; `dev_environment_filter(...)` limits data scanned in dev.

## Complete annotated example

```sql
with my_data as (
    select
        field_1,
        field_2,
        field_3,
        cancellation_date,
        expiration_date,
        start_date
    from {{ ref('my_data') }}
),

some_cte as (
    select
        id,
        field_4,
        field_5
    from {{ ref('some_cte') }}
),

some_cte_agg as (
    select
        id,
        sum(field_4) as total_field_4,
        max(field_5) as max_field_5
    from some_cte
    group by 1
),

joined as (
    select
        my_data.field_1,
        my_data.field_2,
        my_data.field_3,
        -- use line breaks to visually separate calculations into blocks
        case
            when my_data.cancellation_date is null
                and my_data.expiration_date is not null
                then expiration_date
            when my_data.cancellation_date is null
                then my_data.start_date + 7
            else my_data.cancellation_date
        end as cancellation_date,
        some_cte_agg.total_field_4,
        some_cte_agg.max_field_5
    from my_data
    left join some_cte_agg
        on my_data.id = some_cte_agg.id
    where my_data.field_1 = 'abc' and
        (
            my_data.field_2 = 'def' or
            my_data.field_2 = 'ghi'
        )
    having count(*) > 1
)

select * from joined
```
